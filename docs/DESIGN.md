# Design explanation

## Overview

AI interprets the parent. Ordinary code does everything else. eSchool's filters find candidates, but
only what a school's own page says can be claimed about it.

Probing the live site showed why that split matters. Its fee filter returns schools with no published
tuition, its Kampala filter returns other districts, and "open admissions" matches nothing nationally.
An assistant that trusted the filters would give confident, wrong answers.

## How the solution works

```
parent's text
   │
   ▼
Interpreter (Gemini)        one schema-constrained call → ParentRequest
   │                        (keyword fallback if Gemini is unavailable)
   ▼
Review                      asks first if searching would be pointless or wrong
   │
   ▼
Resolve vocabulary          district and area checked against the site's own lists
   │
   ▼
Search with relaxation      strict search, then drop filters in a set order, restore unneeded ones
   │
   ▼
Verify                      load top profiles, check every criterion, record evidence
   │
   ▼
Response                    criteria, assumptions, notes, questions, schools, search steps
```

Each stage is separate and testable. Only `interpreter/` knows AI is involved, and everything after it
works with a validated `ParentRequest`. That is why a bad model output can at worst cause a bad search,
not an invented fact.

## From natural language to search criteria

`ParentRequest` captures what the parent said, not yet what the site can do:

- **Specified and unspecified stay distinct.** Empty means not stated, and the response lists those.
- **Firmness is captured per criterion.** "Preferably around Central Division" is `preferred`, while "no
  more than 1 million" is `required`. This decides what may be relaxed later.
- **Local usage is in the prompt:** S.1 is secondary, "800k" is an amount, a quoted fee is a maximum.
  "Affordable" sets no number and prompts a question instead.
- **Beliefs are declared.** If the model places Ntinda in Nakawa Division, that goes in `assumptions`, and
  the parent sees it.
- **Wishes with no filter are not approximated.** "Best UCE results" goes in `unsupported_preferences` and
  is reported as not applied.

`query.py` then maps this to real parameters, including the site's quirks: fees as plain digits, boarding
as two requests, primary as both `Primary` and `Nursery & Primary`.

Model output is not trusted on names. A district must exist in the site's list and a county must exist
under that district, or it is treated as unresolved and the parent is told.

## How the application interacts with eSchool

The search is a public GET form, so the app builds the same URLs a browser would and parses the HTML.
Internal endpoints are not used. See [ESCHOOL_INTEGRATION.md](ESCHOOL_INTEGRATION.md) for the parameters
and findings.

Search cards show little, so the top 8 candidates' profiles are read for gender, section, county, fees and
facilities. Requests are capped at three at a time, retried, and cached for an hour, because the site is
slow. This reuses eSchool's search and stores no separate dataset. The cache is only short-lived pages.

## Why this AI integration and technical approach

**One structured-output call, not an agent.** The task is extraction with a known schema. A tool-calling
loop would add cost, latency and failure modes with no gain, as the search steps are fixed and need to be
predictable. Gemini's structured output gives a schema-valid response, which is validated again with
Pydantic.

**Gemini Flash-Lite at low effort.** Extraction from a short message does not need deep reasoning, and a fast
model suits a search where the slow step is eSchool. `gemini-3.5-flash-lite` has a free tier, which fits a
prototype. It answered in under 2 seconds in testing, while `gemini-3.8-flash` timed out repeatedly, so
a failed call now costs at most about 40 seconds before the keyword fallback takes over. A production version should use a paid tier, because Google's free tier may use submitted
content to improve its products, and a parent's message can be personal. `ESCHOOL_MODEL` changes the model.
The app calls Gemini through its OpenAI-compatible endpoint, so another provider is a small change.

**School data never goes to the model.** Match explanations are generated by code from page evidence, so
there is no way for a model to invent or embellish a school detail. It also fits the site's declared
`use=reference` signal. The explanations are plainer than a model would write, but every one of them can be
traced to a page.

**Every field is required in the schema sent to Gemini** (nullable or empty when unused). This makes the
model address each criterion instead of skipping it by omission.

**Python, httpx, BeautifulSoup, Pydantic, FastAPI.** These are small and well understood. The web UI is one
page.

## Handling ambiguity, missing information and failures

| Situation | Behaviour |
| --- | --- |
| Too vague to search ("a good school") | Asks before searching |
| Contradiction (minimum above maximum) | Asks before searching |
| Area with no district | Asks before searching |
| Useful but incomplete | Searches, then asks what would improve results |
| Parent answers a question | The answer joins the request and the search runs again |
| Unsupported wish | Reported as not applied |
| Neighbourhood not on the site | Uses a validated division with a stated assumption, or widens and says so |
| District not on the site | Says so and asks about nearby districts |
| No school meets everything | Relaxes filters, shows every step, labels results as closest options |
| Strict search over-relaxes | Restores any dropped filter that was not the real blocker |
| Required gender, level or district | Never relaxed: those would not be real alternatives |
| Tuition not published | "Unconfirmed", quoting the page. Never assumed to fit |
| Facility not listed | "Unconfirmed", not "does not have it" |
| Profile contradicts a request | School is left out, and named with the reason |
| Admission by class | Always unconfirmed, because the site does not publish it |
| Site down or timing out | Retries, then a clear failure. Never "no schools found" |
| Site layout changed | Detected and reported as a failure, not read as empty results |
| One profile fails | That school's details are shown as unconfirmed |
| Gemini unavailable or invalid output | Falls back to keywords and says so |
| Text in the request tries to instruct the model | Treated as data, and the schema limits any effect |

Results are labelled `matches` only if no filter was dropped and nothing contradicts the request. "Matches"
does not mean every fact is confirmed: each school shows ✓, ~, ? or ✗ per criterion, so the parent can see
the difference.

## What I would improve with more time

1. **An evaluation set for the interpreter**, with labelled parent messages covering Ugandan phrasing,
   mixed languages such as Luganda, and adversarial input. Prompt or model changes would then be measured.
2. **Real multi-turn conversation.** Today a parent's answer is added to their request and the whole
   search runs again, which needs no server state. Stored sessions could handle corrections better.
3. **Better Kampala coverage**, by searching all eight divisions when the parent means Kampala proper.
4. **A public eSchool search API.** It would replace HTML parsing and could expose real tuition, day and
   boarding fees, and admission by class. Those gaps limit the answers more than anything in this code.
5. **Fixes on eSchool's side:** comma-formatted fees, the `Open for 2026` badge conflict, and the Kampala
   filter's scope.
6. **Monitoring for parser drift**, by running the live contract tests on a schedule.
